# Отчёт по реализации мультиагентной системы

## 1. Структура файлов

### 1.1. Виртуальная доска задач (`task_board.md`)
- **Назначение**: Единственный канал общения агентов.
- **Содержит**:
  - Активные задачи (статус: `pending`, `assigned`, `in_progress`, `completed`, `failed`, `review`).
  - Завершённые задачи.
  - Очередь задач.

### 1.2. Контекст задач (`context/task_1.md`)
- **Назначение**: Хранение контекста для каждой задачи.
- **Содержит**:
  - Описание задачи.
  - Файлы, участвующие в задаче.
  - Результаты выполнения.
  - Обратную связь от критика.

### 1.3. RAG (`rag/solutions.md`)
- **Назначение**: Хранение успешных решений для повторного использования.
- **Содержит**:
  - Запросы и решения в формате Markdown.

## 2. Реализованные инструменты менеджера

### 2.1. `decompose_task`
- **Описание**: Декомпозирует задачу на подзадачи и назначает их агентам.
- **Параметры**:
  - `task`: Описание задачи.
  - `maxAgents`: Максимальное количество агентов (по умолчанию 3).
- **Действия**:
  - Создаёт подзадачи в `task_board.md`.
  - Назначает ответственных агентов (Кодер, Тестировщик, Критик).
- **Пример вызова**:
  ```json
  {
    "task": "Рефакторинг модуля авторизации",
    "maxAgents": 3
  }
  ```

### 2.2. `assign_task`
- **Описание**: Назначает подзадачу агенту и обновляет статус на доске.
- **Параметры**:
  - `taskId`: ID подзадачи (например, `task_1`).
  - `agent`: Имя агента.
- **Действия**:
  - Обновляет статус задачи на `assigned`.
- **Пример вызова**:
  ```json
  {
    "taskId": "task_1",
    "agent": "Кодер"
  }
  ```

### 2.3. `check_result`
- **Описание**: Проверяет результат выполнения задачи и обновляет статус на доске.
- **Параметры**:
  - `taskId`: ID задачи.
  - `status`: Статус задачи (`completed`, `failed`, `review`).
  - `result`: Результат выполнения.
- **Действия**:
  - Обновляет статус задачи на доске.
  - Если задача провалена (`failed`), отправляет её в очередь на повторное выполнение.
- **Пример вызова**:
  ```json
  {
    "taskId": "task_1",
    "status": "completed",
    "result": "Функция login() рефакторирована, тесты прошли успешно."
  }
  ```

### 2.4. `rag_store`
- **Описание**: Сохраняет успешное решение в RAG.
- **Параметры**:
  - `query`: Вопрос или задача.
  - `solution`: Решение или ответ.
  - `metadata`: Дополнительные метаданные (агент, дата).
- **Действия**:
  - Добавляет решение в `rag/solutions.md`.
- **Пример вызова**:
  ```json
  {
    "query": "Как рефакторить функцию авторизации?",
    "solution": "Использовать паттерн Strategy. Пример кода: ...",
    "metadata": {
      "agent": "Кодер",
      "date": "2026-08-07"
    }
  }
  ```

### 2.5. `rag_search`
- **Описание**: Ищет похожие решения в RAG по запросу.
- **Параметры**:
  - `query`: Запрос для поиска.
- **Действия**:
  - Возвращает список решений, соответствующих запросу.
- **Пример вызова**:
  ```json
  {
    "query": "Как улучшить покрытие тестами?"
  }
  ```

## 3. Логика работы системы

### 3.1. Workflow
1. **Пользователь** отправляет задачу в чат.
2. **Менеджер** вызывает `decompose_task` для разбиения задачи на подзадачи.
3. **Менеджер** вызывает `assign_task` для назначения подзадач агентам.
4. **Агенты** выполняют задачи:
   - Кодер: рефакторит код.
   - Тестировщик: пишет тесты.
   - Критик: анализирует качество.
5. **Менеджер** вызывает `check_result` для проверки результатов.
6. Если задача выполнена успешно, менеджер вызывает `rag_store` для сохранения решения.
7. При новой задаче менеджер вызывает `rag_search` для поиска похожих решений.

### 3.2. Ограничение параллелизма
- Максимальное количество агентов: **3** (настраивается в `decompose_task`).
- Если все 3 агента заняты, новые задачи ставятся в очередь.

## 4. Пример работы

### 4.1. Входная задача
```
Пользователь: "Рефакторинг модуля авторизации."
```

### 4.2. Декомпозиция (`decompose_task`)
```markdown
## Очередь задач
- [x] task_1: Рефакторинг функции login() в src/auth.ts (Кодер)
- [x] task_2: Написание unit-тестов для auth.ts (Тестировщик)
- [x] task_3: Анализ покрытия тестами (Критик)
```

### 4.3. Назначение задач (`assign_task`)
```markdown
## Активные задачи
| ID       | Описание                          | Агент      | Статус      | Результат                     | Дата       |
|----------|-----------------------------------|------------|-------------|-------------------------------|------------|
| task_1   | Рефакторинг функции login()       | Кодер      | assigned    | -                             | 2026-08-07 |
| task_2   | Написание unit-тестов             | Тестировщик| assigned    | -                             | 2026-08-07 |
| task_3   | Анализ покрытия тестами           | Критик     | assigned    | -                             | 2026-08-07 |
```

### 4.4. Выполнение задач
- **Кодер**: Рефакторит `auth.ts`, обновляет статус на `completed`.
- **Тестировщик**: Пишет тесты, обновляет статус на `completed`.
- **Критик**: Анализирует код, обновляет статус на `review`.

### 4.5. Проверка результатов (`check_result`)
```markdown
## Завершённые задачи
| ID       | Описание                          | Агент      | Статус      | Результат                     | Дата       |
|----------|-----------------------------------|------------|-------------|-------------------------------|------------|
| task_1   | Рефакторинг функции login()       | Кодер      | completed   | Функция обновлена, сигнатура сохранена | 2026-08-07 |
| task_2   | Написание unit-тестов             | Тестировщик| completed   | Тесты прошли успешно          | 2026-08-07 |
| task_3   | Анализ покрытия тестами           | Критик     | review      | Код чистый, но нужна валидация входных данных | 2026-08-07 |
```

### 4.6. Сохранение в RAG (`rag_store`)
```markdown

### Запрос: "Как рефакторить функцию авторизации?"
**Решение**:
```markdown
- Использовать паттерн Strategy для разделения алгоритмов авторизации.
- Пример кода:
```typescript
class AuthStrategy {
  login(credentials: Credentials): User | null {
    // Реализация
  }
}
```
```
```

## 4. Мультитаск и параллелизм

### 4.1. Диспетчер задач (`TaskDispatcher.ts`)
- **Назначение**: Управляет очередью задач и распределяет их между агентами.
- **Ограничение параллелизма**: Не более 3 агентов одновременно.
- **Приоритеты задач**: Высокий, средний, низкий.
- **Методы**:
  - `addTask`: Добавляет задачу в очередь.
  - `assignTask`: Назначает задачу агенту, если есть свободные слоты.

### 4.2. Пример очереди задач
```markdown
## Очередь задач (приоритет)
1. [ ] task_1: Рефакторинг auth.ts (Кодер, высокий)
2. [ ] task_2: Написание тестов для auth.ts (��естировщик, высокий)
3. [ ] task_3: Анализ покрытия тестами (Критик, средний)
```
